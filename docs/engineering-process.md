# 调研、决策与验证规则

生效日期：2026-11-05。来源：用户明确要求，适用于新项目所有模块。

每个模块必须回答：谁遇到了什么问题，同类产品如何处理，我们有哪些选择，为什么这样选，怎样验证，实际效果与局限是什么。

## 开发前

| 步骤 | 需要完成的工作 | 留存证据 |
| --- | --- | --- |
| 问题定义 | 明确用户任务、输入、期望结果和影响 | 用户场景、数据条件、失败样本或待验证假设 |
| 建立基线 | 复现已有缺陷；新能力先建立简单参照方案 | 固定输入、手工核算结果、可运行复现程序及实际输出 |
| 同类调研 | 通常比较 2–3 个直接相关产品或框架，说明适配差异 | 官方链接、日期、版本或 commit、能借鉴的机制 |
| 方案比较 | 包含保持现状或最小实现、借鉴实现、采用现成组件 | 收益、复杂度、可靠性、学习与维护成本、使用限制 |
| 决策与验收 | 说明选择理由、代价、实施范围、回退和重选条件 | ADR 或包含全部环节的模块记录、验收方案 |

没有直接同类时，解释为什么借鉴邻近场景。实现级结论需查看源码或实验；产品文档只支持其声明的能力。招聘 JD 用于能力映射，不能代替产品调研。

开发前向用户说明结论和验证计划。用户已授权范围内自主推进，不机械增加确认环节。若涉及重大范围变化、真实数据授权、付费资源等缺失条件，再提出具体问题。

## 实施与实验

1. 每次完成一个可验证目标。先使用成熟组件解决通用问题，自研部分须说明必要性。
2. 模块实施前保存可恢复的源码基线，使用 Git commit 或独立快照，并保留 SHA-256 清单。不可只保存文件名或变化后的源码。
3. 固定数据版本、语义口径、模型标识、Prompt、工具版本、依赖、环境和预算。记录日期、命令、原始输出与执行轨迹。
4. 确定性测试验证计算、权限、状态和契约；真实模型评测验证任务效果。两者分别报告。
5. 模型回答不承诺逐字一致。复现要求是环境可重建、数据和口径可定位、计算可重算、模型实验可按同一方法重复并报告波动。
6. 运行与变更相关的检查。效果不足或发生退化时修正或回退，保留失败证据。

多 Agent 实验至少与强单 Agent 加相同工具比较。控制模型、数据、工具能力与预算，分别报告质量、调用量、费用和时延；提高预算获得的结果不能归因于架构本身。测量阈值须在评测前约定，不在看到结果后调整。

## 记录与表达

模块记录位于 `docs/research/`；正式选型可追加 `docs/adr/`；实验位于 `docs/probes/`；阶段状态位于 `docs/baselines/`。小模块可合并记录，避免机械生成文档。

状态区分：调研中、方案待验证、已决策待实施、已实施待验证、已验证、已放弃。

证据区分：已观察事实、外部资料声明、我们的推断、预期目标。历史记录保留原始结论，后续通过新记录说明修正。

每个已验证模块应形成一段可复述的面试说明：业务背景、问题、调研、取舍、实现、结果、局限。未上线不能写生产经验，未试用不能写用户收益，模拟数据不能写真实商家数据，模型自评不能单独充当正确性证据。

## 完成标准

一个模块只有在实现、适当验证、可复现证据、必要使用说明齐全时，才标记为已验证。完整项目还须通过干净环境部署、外部数据适配、权限边界、故障恢复和真实模型任务评测，并明确用户试用结果及未验证项。

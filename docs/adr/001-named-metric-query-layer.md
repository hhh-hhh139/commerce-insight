# ADR 001：首版使用命名指标工具，底层复用 DuckDB

日期：2026-11-06。状态：已决策并完成本地验证。适用范围：首版有限电商指标；不排除后续增加 Wren。

## 问题和比较依据

需要把订单、明细和退款流水组合成可以核查的结果，同时控制 Agent 可以执行的操作。业务口径、数据粒度和权限不能只写在提示词里。

先参考 Looker 对称聚合、Shopify 退款状态及 Wren 的 MDL／SDK，再固定样例、金额和验收条件，详见 [实施前约定](../research/002-multitable-query-plan.md)。实际比较使用同一份规范化快照、同一版本 DuckDB 和相同 15 个任务；输入验证两边共用，不把它的收益算作某个查询引擎的优势。

## 实测与取舍

| 维度 | B：命名指标＋参数化 DuckDB | C：Wren SDK＋MDL＋DuckDB |
| --- | --- | --- |
| 固定业务任务 | 15/15 与预期一致 | 修正建模后 15/15 与预期一致 |
| 防止错误聚合 | 指标实现固定正确的粒度，调用者不能提供 SQL | 关系聚合字段有效；任意错误 join SQL 仍可能算错 |
| 执行边界 | 只接收指标名和类型化参数；数据库只读，外部访问关闭后锁定配置 | 显式 strict mode；已测写操作、未建模表、文件读取、多语句及来源生成函数均拒绝 |
| 可追踪性 | 保存 SQL、绑定参数、数据与指标／代码版本 | 可保存模型、输入 SQL 和展开后的计划 |
| 接入工作 | 三表契约及有限业务 SQL | 同样需要契约，另维护 MDL／关系／计算字段及 SDK 参数适配 |
| 擅长的扩展方向 | 明确、有限、需要稳定复算的指标 | 更多数据域、关系复用、自由探索与语义查询 |

这是功能和集成观察，不是完整安全审计或性能排名。原始数据只有 5 张订单，不能推断大数据吞吐、并发容量或真实模型效果。

## 决策

首版默认采用 B：由 Agent 选择命名指标和参数，Python 工具执行已验证的查询，数值从工具返回。底层 SQL 执行复用 DuckDB，业务代码只维护输入契约、八类指标与证据，不自建通用 SQL 解析器或规划引擎。

理由：当前任务可以用有限指标表达；B 已通过本轮正确性与基本执行边界检查，能够更直接限定可执行范围。引入 Wren 在本轮没有带来数值正确性增益，而多一套模型与适配需要维护。**Wren 能力已实测，不因第一次接入错误或依赖下载困难而被否定。**

保留 Wren 的固定版本模型和完整实验。若后续新增数据域、字段关联与自由探索任务使固定工具明显受限，重新评估 Wren；比较真实模型任务完成率、建模／维护成本、预算和执行边界。不能用这 15 个确定性任务声称它在复杂问题上也没有优势。

代价：新增业务指标需要代码和回归验证；当前不能让用户任意写 SQL，也没有任意行业自动建模。该限制是首版明确的产品范围。

## 已实现与未实现

`commerce_data/ledger.py` 负责规范化三表契约与指标规格，`ledger_db.py` 负责只读查询和证据，`ledger_cli.py` 提供本地运行入口。现有单文件工具保持可用。Wren 留在 `experiments/query-layer/`，不进入首版运行依赖。

Java 以后负责用户授权、数据版本及任务；传给 Python 的 workspace 必须已经授权。当前 workspace 相等检查不等于身份认证。LangGraph 以后调用这些工具，单 Agent 基线及必要的多 Agent 分工仍需真实模型实验。

# 多表口径与查询层对比：实施前约定

准备日期：2026-11-05。验证完成：2026-11-06。以下保留实施前约定；结果见 [实测记录](../probes/query-layer-2026-11-06.md)，最终选择见 [ADR 001](../adr/001-named-metric-query-layer.md)。固定版本候选 Wren 0.17.1 已实际执行，不再停留于文档比较。

## 要解决的问题

用户需要同时分析订单、商品明细和退款流水。直接关联会把订单总额重复计算；退款记录存在不等于退款成功；按发生时间统计和按原订单归属统计会给出不同答案。上一轮只有销售／取消明细，不能据此声称已完成退款分析。

本轮交付：独立三表数据契约、有限查询工具，以及受控 SQL 与 Wren SDK 对同一固定输入的执行比较。使用新合成流水，不把 UCI 的取消记录改名成现金退款。

## 同类研究

查阅日均为 2026-11-05；在线文档为滚动版本，包实现固定到实际下载的版本。

- [Looker 对称聚合](https://docs.cloud.google.com/looker/docs/best-practices/understanding-symmetric-aggregates)：关系造成行数膨胀时，主键和聚合粒度影响正确性。借鉴先明确实体身份与关系，不复制其专用哈希聚合。
- [Shopify Refund](https://shopify.dev/docs/api/admin-graphql/latest/objects/Refund) 及[查询说明](https://shopify.dev/docs/api/admin-graphql/latest/queries/refund)：需要检查关联交易状态才能确定退款实际成功。我们的输入是已规范化成功状态的退款交易，不能直接把任意平台 Refund 对象塞进来。
- [Wren 架构](https://docs.getwren.ai/oss/reference/architecture)、[SDK](https://pypi.org/project/wrenai/0.17.1/)：通过显式 MDL 规划查询，再交由数据源执行。验证业务模型和关系路径能提供哪些帮助，也检查错误 SQL 是否仍会得到错误数字。
- [DuckDB 安全说明](https://duckdb.org/docs/2.0/operations_manual/securing_duckdb/overview)：只读数据库与外部文件访问限制是不同边界。测试仅用本项目内的合成文件和数据库，绝不读取电脑上的其他文件做安全探测。文档 2.0 不等于最终实验安装版本；以实际版本和行为为准。
- [uv 环境配置](https://docs.astral.sh/uv/reference/environment/)：Python、缓存和可执行文件目录可以显式指定。本轮隔离安装在 `.local/`，不修改全局解释器、Git、SSH 或凭据配置。

## 固定输入契约

一份数据快照只包含一个明确 workspace、一个币种；本轮样例为 CNY、整数分。业务时刻必须携带 UTC 偏移，并规范化为 UTC。按 `[start,end)` 筛选。快照不声称保留历史状态演变或完整会计账簿。

| 表 | 粒度及字段 | 关键验证 |
| --- | --- | --- |
| orders | order_id、status、paid_minor、paid_at、currency | 主键唯一；paid 状态有正金额和时间；未支付状态为零金额且无支付时刻 |
| items | item_id、order_id、product_id、line_minor | 明细主键唯一、所属订单存在；本简化契约要求支付订单明细金额合计等于支付金额，不含额外运费／税费分摊 |
| refunds | refund_id、order_id、item_id（可空）、status、amount_minor、refunded_at、currency | 流水唯一、关联存在；仅 succeeded 计入金额；成功退款有发生时刻且不早于支付；累计成功退款不超过原支付金额 |

缺失退款表表示能力不足，不能默认为“退款为零”。明示空表才是本快照提供的零条退款记录，仍依赖导出完整性。退款没有 item_id 时可以分析订单退款，不能自动按订单金额比例分摊成商品退款。绑定 item_id 时必须属于该订单，且累计不超过对应明细金额。

固定样例：第一期 A 支付 10000（两条明细 6000、4000）、B 支付 8000、C 支付 10000；第二期 D 支付 15000。第二期 A 成功退 2000 和 1000、B 成功退 2000；另含失败和处理中退款，不进入统计。第三期 C 成功退 1000，用于检查截止时间。另有未支付订单。

预先期望：第一期支付 28000，第二期支付 15000、成功退款 5000、发生口径净额 10000；第一期订单截至第二期末的支付减成功退款为 23000；第一期发生退款的订单数为 2／支付订单数 3。第三期退款不能穿越截止时间。两张同额订单不能被 DISTINCT 金额误删。

## 公平比较与验收

1. 使用相同规范化三表、相同底层 DuckDB（如果 SDK 可连接本地库）、相同指标含义及固定 SQL 意图。输入校验为两者共用，不把自研额外校验的收益算作查询引擎优势。
2. B：按指标名和类型化参数调用参数化 SQL，不向 Agent 开放任意 SQL。C：通过 Wren SDK 的显式 MDL／connection 执行同等查询并保留规划后 SQL；不使用全局 profile 或机器上的既有连接。
3. 查询预期金额全部精确一致；统计订单数按主键处理；不同时间口径独立命名。参数含 SQL 字符时不改变查询结构。未知指标或数据不足明确拒绝。
4. 错误输入检查主键重复、孤儿引用、币种混杂、未知状态、时区缺失、退款早于支付、超额退款及错误商品关联。失败不得给出看似正常的金额。
5. 除常规等价 SQL，增加 Wren 关系表达实验和故意错误的直接 join 聚合对照，观察其能做什么、不能保证什么。
6. 在项目专属临时库检查写操作、未建模表和外部文件访问边界。只使用自己创建的哨兵文件，不访问真实用户／公司文件；未执行或未覆盖的边界如实列出。
7. 记录安装依赖、源码配置、适配代码、输出、版本、模型定义与输入哈希。小数据耗时仅是观测，不推断大规模吞吐或生产性能；不以安装失败代替框架能力评价。

本轮是确定性开发验证，不含模型、Prompt 或收费 API，也不是独立模型保留集。后续真实 Agent 评测需另外设计。

## 选择规则

优先选择能满足当前固定指标任务、执行边界明确且集成负担合理的方案。若 Wren 关系模型显著减少必要逻辑并能清楚控制执行边界，可采用；若有限工具足够，则以其作为首版查询路径，并保留 Wren 扩展入口。当前不提前认定胜者。

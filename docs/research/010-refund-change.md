# 010 · 退款变化定位：先分清发生期，再讨论商品归属

日期：2026-11-06。范围：个人项目；合成账本；无外部退款操作。

## 问题与复现

现有 `refund_amount` 可以正确计算期间成功退款，但不能解释两期变化集中在哪里，无法同时看到早期订单影响和缺失商品归属。已有商品退款指标遇到缺失归属会拒绝，这个严格口径继续保留。

`docs/probes/refund-change-before-2026-11-06.json` 记录正确标量 5000 分与错误候选关联 8000 分：按订单关联商品明细会把一笔退款重复到多个商品。这是被否决方案的反例，不是声称现有标量有 bug。源码基线：`.local/baselines/before-refund-change-20261106/manifest.json`。

## 方案比较与决定

1. **给现有标量加前端百分比**：成本低，但退款/本期支付混合订单批次；无法定位归属，放弃。
2. **订单关联商品后分摊或让模型生成 SQL**：看似覆盖完整，缺乏可信分摊依据，可能重复计数；放弃。
3. **新增命名工具 `refund_change`，确定性 SQL + 不完整归属显式披露**：复用任务、快照、Agent 工具调用和证据发布链路，采用。无需为一个描述性分析增加 Agent。

两期必须等长、按时间排序、不重叠，均采用显式时区和左闭右开区间。只统计 `succeeded`，按退款发生时间选记录。每期分为该期开始前支付的 `prior_orders` 和该期内支付的 `same_period_orders`。商品只通过退款的 `item_id` 唯一关联；缺失归属单列，禁止按订单金额强行分配。商品按绝对变化排序，Top N 之外合并为其他已关联商品；不宣称这是全部商品的真实排名。

输出总金额、变化率（零分母返回 null）、退款笔数、去重退款订单数、订单来源、商品归属金额覆盖率、已关联商品变化、其他和未归属金额。两个独立标量总额分别与分组金额核对，Java 再核对报告绑定和算术；Python 审计重建数据库重算。Java 不是独立 SQL 真值验证。

不称“退款率”或统计异常，不声称退款原因、利润、质量问题或真实经营改善。当前数据没有退款原因字段，也没有充分的历史季节性样本。

## 验收预先约定

- 10/05–10/12 对 10/12–10/19（UTC）：0→5000 分；本期 3 笔、2 单；早期订单 5000 分；已关联 3000 分、未归属 2000 分，覆盖率 60%。
- 10/12–10/19 对 10/19–10/26：5000→1000 分，变化 -4000 分（-80%）；P1 -2000、P2 -1000、P3 +1000、未归属 -2000 分。
- 验证失败/待处理排除、部分退款不重复、缺表拒绝、空期、零分母、半开时间边界、同期间订单、Top N 余项、只读工具与能力限制、伪造结果拒绝。
- 验证 Java→Worker→DuckDB→Java 与 LangGraph 离线链路；真实模型需另行执行个人评测，离线通过不算模型理解能力。
- 阶段报告保存首次失败及修复、最终原始结果和源码快照；随后继续原计划的报表差异核对。

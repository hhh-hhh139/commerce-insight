# 销售变化的商品贡献分析

日期：2026-11-06。开发前决策；阶段实测另行记录。

## 问题与基线

用户能看到支付金额 280 → 150 元，但无法得到商品层面的变化分解。现有 `paid_amount_for_product_orders` 是包含某商品的**整单金额**，不能相加当商品销售额；实测 P1/P2/P3 的基期整单金额分别 180/100/100 元，相加 380 元，超过总额 280 元。这是指标适用范围，不是原指标实现错误。见 `docs/probes/sales-change-before-2026-11-06.json`。

已确认账本含订单实付额与分摊明细金额，且所有支付订单必须满足明细和等于支付额。利用这一契约，首版明确分析**已支付金额的商品贡献，不扣退款**，按订单支付时间落入区间。不把此口径等同 Shopify 净销售额、到账或利润。

## 方案比较

1. 保留总额比较，让用户逐商品查询：改动少，但现有整单指标不满足分摊需求；多次调用还有漏商品、上下文与工具次数成本。
2. LLM 生成自由 SQL 或多个专家各算商品：灵活，但引入不必要的查询/汇总与协调风险，无法证明本阶段收益。
3. 接入完整 BI 引擎：通用图表与维度丰富，但现阶段一个可加指标、一个商品维度，无需增加部署和语义维护面。
4. **新增固定参数的确定性分解工具，复用 DuckDB 与单 Agent**：一次受控分析得到两期全商品聚合、独立订单总额与勾稽，代码负责差值/比例/排名，模型仅选工具与参数、引用证据。

不改旧指标定义、旧数据契约或已确认版本。新分析基于已有 `paid_amount` 能力与账本明细契约开放，因此缺退款表的旧导入版本也可使用，无需改写其历史能力记录。新的工具、Prompt 和实现哈希单独记录；历史真实模型成功率不沿用为本版质量。

## 输出契约与边界

- 两个显式含时区的半开区间，基期早于对比期、等长、不重叠，可不相邻，均不超过快照覆盖截至时间。明确对比区间由用户提供，不能把“上周”自行填成样例日期。
- 聚合粒度是 product_id；同一订单同一商品多条明细相加。退款表不参与 JOIN，不做数量×单价分解（当前没有这些字段）。
- 全量各商品 `delta = current - baseline`；各商品两期金额之和分别等于订单总额，各商品 delta 和等于总变化，否则拒绝发布。
- 增长与下降各展示最多 top_n（默认 5，上限 10）；先按变化绝对金额，再按 product_id 稳定排序；各方向剩余商品的数量和金额保留。零变化商品只给数量，不挤占榜单。
- “下降贡献占比”分母是所有下降商品的下降金额绝对值；增长同理。**不是占净变化的比例**，避免正负抵消导致超过 100% 或除零；比例四舍五入两位，不承诺显示值相加恰好 100%。
- 总体或商品基期为零时，增长率返回 null，显示不可计算；本期有额/基期无额不等于新上架，本期为零不等于下架。总变化为零仍显示正负抵消，双期无额不编造主要商品。
- 输出总览、主要下降/增长、其他贡献、完整勾稽、SQL 与绑定参数、数据/实现哈希。证据报告仍由代码生成，不接受模型撰写金额或因果说明。
- 人工表单和 Agent 调用同一计算实现；Java 校验请求、版本权限、来源/区间/结果契约和派生金额守恒。Python Worker 是受信服务；Java 不是独立 SQL 重算引擎。

## 实施前验收

固定样例必须为总变化 -130 元：P3 -100、P2 -40、P1 +10，下降 140 被增长 10 抵消；P3 占下降金额 71.43%。另测新增期间有额/归零、双期无额、总额不变但正负抵消、零基数、重复商品明细、多笔退款不扩行、取消单、日期边界、非法/不等长期间、Top N 的其他贡献、排序、较大金额和独立 Python 汇总对照。

集成覆盖内置与两套导入版本、未确认与模型许可、离线真实 LangGraph 选工具/引用/拒绝伪造、Java 拒绝错误结果和越权、网页提交/报告/证据/刷新。按变更回归旧数据、导入、任务与 Agent；本轮不持有个人 Key，不发起付费模型请求，不以脚本模型测试代替真实模型效果。

前端只增加必要的日期、分析入口与结果表格，整体美化按用户要求后置。仍限定个人项目本机，不操作远端或公司资源。

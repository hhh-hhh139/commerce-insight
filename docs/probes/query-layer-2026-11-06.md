# 多表契约与查询层实测

准备开始于 2026-11-05，验证完成于 2026-11-06。全部使用本项目合成数据、独立临时数据库和项目内运行环境；没有模型调用、生产数据或公司系统访问。

## 固定问题与结果

样例：第一周 A、B、C 分别支付 100、80、100 元，其中 A 有两条明细；第二周 D 支付 150 元，A 分两次成功退 20 和 10 元，B 成功退 20 元；第三周 C 成功退 10 元。失败／处理中退款另列，未支付订单不计入支付金额。

| 问题 | 手工预期，CNY | 受控查询 | Wren SDK |
| --- | ---: | --- | --- |
| 第一周支付金额 | 280 元 | 一致 | 一致 |
| 第二周支付金额／成功退款金额 | 150／50 元 | 一致 | 一致 |
| 第二周按发生时间的支付减退款 | 100 元 | 一致 | 一致 |
| 第一周订单截至第二周末的支付减退款 | 230 元 | 一致 | 一致 |
| 同批订单截至第三周末 | 220 元 | 一致 | 一致 |
| 第一周支付订单／截至第二周末成功退款订单 | 3／2 单 | 一致 | 一致 |

“支付减退款”不等于会计收入或结算到账。两个时间口径对应不同问题；截至时刻按排他上界处理。退款订单数按订单身份计数，不按退款事件数计数。其他检查包含同额订单、商品订单筛选、SQL 字符参数、空期间和精确时间边界。

全部 **15/15** 固定任务两边都通过。Wren 的两项关系计算字段实验也通过：A 的明细合计 10000 分，成功退款合计 3000 分。原始输出：[最终比较报告](query-layer-2026-11-06.json)。

## 为什么仍需控制业务口径

内部直接执行同样的错误 SQL 时，两种底层查询路径均得到：

| 错误写法 | 结果 | 正确结果 |
| --- | ---: | ---: |
| 关联明细后 SUM 订单金额 | 38000 分 | 28000 分 |
| SUM(DISTINCT 订单金额) | 18000 分 | 28000 分 |

这些是故意构造的反例，不是正常任务失败率。B 的命名指标接口不接收这类任意 SQL；Wren 可以正确执行 SQL，却不能仅凭查询推断提问者是否选错了业务粒度。Wren 的已建模关系聚合可降低特定建模路径的重复风险，不意味着任意 join 自动正确。

## 数据及执行边界

数据契约拒绝主键重复、孤儿记录、币种混杂、未知状态、缺时区、退款先于支付、订单／商品超额退款以及商品归属错误。未提供退款表时拒绝退款指标；明确提供空表时才按该快照中的零条记录计算。没有商品关联时拒绝相关期间的商品级退款查询，不按比例猜测归属。

执行层有 7 个边界观察：受控数据库的写入和外部文件读取被拒；Wren 严格 SDK 的写入、未建模表、外部文件、多语句及来源生成函数被拒。仅使用本项目内自建哨兵 CSV，未探测其他本地文件。实验前后数据库哈希一致。

这些检查不等于完整沙箱或多租户安全验证。用户授权、任务超时终止、并发限制、故障恢复仍未实现。当前 SDK 使用可信代码提供的 MDL，未测试用户自定义 MDL 的安全性。

## 实际遇到的问题及修正

1. 公开依赖下载发生超时、DNS 失败，以及一次 uv wheel 哈希不符。错误包未使用；改用 curl 下载并按 PyPI 哈希校验后解包 uv 0.13.7。Wren wheel 也核验固定哈希后才检查源码。没有使用全局安装脚本或公司包源。
2. 受控连接最初在打开 DuckDB 时就禁用全部外部访问，阻止其检查自身 `.wal.checkpoint`，9 项数据库测试因此报错。改为可信建库步骤完成后，只读打开指定库，再关闭外部访问并锁定配置，之后才接受指标查询。9 项测试全部通过，写操作和外部文件访问仍被拒。
3. Wren 初始 `SUM(CASE WHEN refunds.status = 'succeeded' THEN refunds.amount_minor ELSE 0 END)` 关系表达报循环依赖，导致首轮仅 3/15 正常任务通过。先在 Refunds 中定义 `successful_amount_minor`，再在 Orders 中 `SUM(refunds.successful_amount_minor)`，相同数据与预期下达到 15/15。我们只确认固定版本下该建模形式的行为，未确认上游根因，不将首轮失败描述为最终框架正确率。[首轮输出](query-layer-initial-2026-11-06.json) 已保留；原模型、脚本及报告在 `.local/query-layer/attempt-01.tar.gz`。
4. Arrow 的部分整数聚合值以 Decimal 返回，首次报告序列化失败。增加保留精度的编码，并检查整数指标确实为整数后才转换，避免截断小数造成假通过。

这些修正没有修改数据和预期答案。最终不以安装困难、未经公平适配的失败或不对等耗时决定方案。

## 决策与可讲述成果

首版采用命名指标＋DuckDB，Wren 保留为扩展候选，详见 [ADR 001](../adr/001-named-metric-query-layer.md)。可以讲述：先复现重复聚合与跨期差异，参考成熟产品，固定同输入对照，修正适配问题后公平比较，再根据首版范围选择较小的执行接口。

不能据此宣称提升 Agent 准确率、节省商家时间或具备生产级多 Agent 能力。它证明的是指定契约和样例范围内的可核算查询及基本边界。

# Java / Python 任务闭环实测

日期：2026-11-06。全部操作限定个人项目；没有使用公司仓库、GitLab、已有 Git/SSH 凭据或全局 Maven 设置。没有推送或部署。

## 环境与输入

- Temurin JDK 21.0.13+9、Maven 3.9.16，官方校验值固定在 `scripts/bootstrap_java.py`。项目内 Spring Boot 4.1.2、Spring JDBC 7.0.10、HikariCP 7.0.2、H2 2.4.240、Jackson databind 3.1.7、Tomcat embed core 11.0.27。
- Python 3.12.16、DuckDB 1.5.0，无新增 Python 第三方依赖；与 Wren 实验环境隔离。
- macOS ARM64，真实 JVM 和 Python 进程，只监听 127.0.0.1。验收租约 1500 ms、退避 100 ms × 尝试次数、最多 3 次；演示默认租约 15 s、退避 1 s × 尝试次数。缩短时间用于故障测试，不混成线上延迟数据。
- 合成快照 SHA-256：`27048415cf67ccf74b818b62d046eb1d80eff6006e3966c8d7491bac25429cd4`。主问题是第一周支付订单截至第二周末的净额，手算 28000 − 5000 = 23000 分。
- [运行依赖及实现哈希](task-loop-environment-2026-11-06.json) 保存打包后的 42 个依赖 JAR 哈希和实现文件哈希。Maven 构建成功，但没有 JUnit 用例；下列跨进程测试才是本阶段可靠性验收。

## 参照与结果

[参照反例原始结果](task-loop-baseline-2026-11-06.json)：独立子进程中的内存队列重启后待执行任务从 1 变成 0；未保护结果追加逻辑在“已提交但响应丢失”的重试下发布 2 次。这是人为构造的最小参照，不是原项目或真实产品故障统计。

| 场景 | 验证结果 |
| --- | --- |
| Java → HTTP → Python → DuckDB → Java | 完整结果与上一阶段 golden JSON 相等，23000 分，证据保留 |
| 8 个客户端同 key 同时提交 | 只有一个 task_id 和一个 CREATED 事件；同 key 不同请求 409；等价时区归一后仍复用任务 |
| 8 个客户端同时领取 | 一个成功领取，其余没有获得该任务；attempt = 1 |
| 过期执行与重领 | 旧完成、续租、失败回传均 409；新租约 attempt = 2，发布一次 |
| 慢执行期间心跳 | 超过原租约时间仍不被其他 Worker 领取，成功且 attempt = 1 |
| 成功响应丢失 | 服务已提交后客户端注入网络错误；Python 重传后成功，SUCCEEDED 事件仍为 1 |
| 重复完成 / 改写结果 | 对象字段顺序改变仍幂等；同租约改金额 409；成功后超过原租约时间重复确认仍幂等 |
| 执行中取消 | Java 禁止发布；Python 发现失效后终止睡眠子进程；晚到完成 409，无结果 |
| 暂时失败与退避 | 退避窗口内不能领取；尝试最多 3 次，最终 FAILED |
| 数据能力不足 | 缺商品退款归属返回 `product_refund_attribution_incomplete`，FAILED，attempt = 1，不重试 |
| Java SIGKILL + 重启 | 文件库恢复排队/运行/成功记录；过期运行任务重领，旧结果拒绝，既有结果不丢 |
| 角色、空间、请求边界 | 错误 token / 错误角色 401，越空间 403，额外路径字段 400，过大 JSON 413 |
| 结果绑定 | 错误数据哈希、指标、期间、币种、浮点金额均 422；正确结果才发布 |
| 输入损坏 | 故意改传输 bytes，SHA 校验失败；不启动执行子进程 |
| 执行超时 | 子进程被终止；最多 3 次尝试后 FAILED |
| Worker SIGKILL | 领取任务的独立 Python 进程被强制终止三次；租约回收有上限，最终 attempts_exhausted |
| 取消与完成竞争 | 4 次双请求竞争，每次一个 200、一个 409，只有一个终态 |
| 注册数据更换 | 先排队再重启 Java 换注册快照；旧任务仍得旧结果，新任务绑定新快照 SHA 和 snapshot_id |

首次 [17 项验收](task-loop-initial-2026-11-06.json) 全部通过，用时 18.333 s；随后补强 Worker 的真实 SIGKILL、具体业务错误回传和数据冻结测试。[最终 18 项验收](task-loop-2026-11-06.json) 全部通过，用时 22.108 s。耗时仅是本机测试套件耗时，不是性能提升或服务延迟指标。

原有 Python 数据与口径回归 **46/46 通过**，用时 4.438 s；本轮没有修改其实现或测试，原始输出保留于 `.local/task-loop-regression.log`。两组测试不是同一种质量指标，不换算为 Agent 任务成功率。

## 实施中发生的失败与修正

首次用机器 Python 3.9 解压工具链时，`tarfile.extractall(filter='data')` 不受支持而退出；未继续使用不带安全过滤的解压。改用项目已有 Python 3.12 完成校验与安全解压，正式引导脚本明确要求支持 data_filter。工具链安装只在 `.local/`，没有改机器 Java 8。

本轮 Java 首次构建通过，初轮 17 项应用验收没有失败；后续改动来自复查，不伪造“修复前失败率”。本地构建日志分别在 `.local/java-toolchain/build-initial.log`，测试日志在 `.local/task-loop-initial.log` 和 `.local/task-loop-final.log`。这些日志不含需公开的业务数据，不纳入发布文件。

## 复现与结论边界

复现入口见 [实验 README](../../experiments/task-loop/README.md)。一键演示使用独立 Python Worker 进程；故障测试大部分在测试驱动进程中调用同一 Worker 入口，计算仍是独立子进程，Worker 强制退出用例另启领取进程。因此不声称所有测试都模拟了完整生产拓扑。

已验证的是指定本地环境的业务任务交付、状态恢复、租约和发布幂等。没有 PostgreSQL、多 Java 实例、主机掉电/磁盘损坏、真实模型调用、费用预算、公开认证、多租户、外部用户或负载基准。单文件 H2、本地角色 token、初始 SQL 建表不能直接成为公开部署配置。

执行次数可能超过 1；一个有效结果发布不等于端到端 exactly-once。对子进程取消的验证是在 Worker 正常接收失效心跳时进行，不能推广成 Worker 自身遭 SIGKILL 后所有孙进程都被操作系统自动清理。

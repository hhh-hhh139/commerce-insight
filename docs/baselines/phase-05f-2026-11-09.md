## 问题、选择与实施

此前只能证明本机组件工作，Dockerfile 和 Compose 配置未实际构建运行。选择在本个人公开仓库的 GitHub hosted Ubuntu 24.04 runner，从源码、新镜像与空卷构建；不访问公司的 Docker、仓库或凭据。测试使用合成账本和临时应用密码，没有模型 Key。

完整调研、方案比较和反例在 [CI 研究记录](../research/019-clean-linux-ci.md)。三轮真实失败先后发现：Mock 测试读取真实日期、IP 证书在地址映射后无法选择、只读应用根目录缺少查询临时挂载。分别修复测试时钟、CI 的默认 SNI、限定目录的 128 MiB tmpfs；生产价格门禁、客户端证书校验、只读根目录继续保留。

- 新卷真实 PostgreSQL + 应用 + Caddy：未登录 401；登录 CSRF、session 轮换、Secure/HttpOnly/SameSite cookie；缺 CSRF 的写入 403；真实 Java→Python→DuckDB 任务成功返回 28000 分；状态接口报告 PostgreSQL。
- 代理内部业务/Worker 路由返回 404；应用 UID 1000、根目录只读、不发布应用宿主端口。
- 重启应用后原报告保留，旧会话失效；重新登录后可以读取结果，退出后再次拒绝访问。此检查验证已完成报告的重启保留，不声称进行了所有处理中任务的容器故障演练。
- 本机补充：实际 Caddy 的无 SNI 反例及修复、错误证书和错误 IP 拒绝，共 4 个观察；真实文件系统下 CLI 的写权限反例和修复；官方 Compose 两组解析检查 0.102 秒。

成功产物 ZIP SHA-256：`adcee8f4c98487088f710b32fa23216558fb8fe14b8cb16c769f242412a0f6ab`。基础镜像精确 tag 和实际 digest 均在公开 JSON 中。CI 按当次解析出的 digest 构建；默认 Compose 仍是精确版本 tag，不能把本次 digest 记录称为永久锁定全部系统包。

# 阶段 2i · 退款变化定位

状态：工具、Java/Worker、离线 LangGraph、页面与专项评分器已验收；**新版 Prompt 和退款工具的真实模型效果未测**。仅个人项目、合成数据，没有调用模型或操作外部经营系统。

## 变化与原因

之前只能看退款标量，或在缺失商品归属时拒绝商品指标。现在按成功退款发生期比较两期，输出退款记录数与去重订单数、原订单支付来源、商品归属金额覆盖率、已知商品变化、其他和未归属金额。既保留信息，也不把缺失归属推测分摊。

参考 Shopify 的事件日期与报告口径区分、Stripe 的独立退款记录与状态语义，选择有限命名工具和确定性报告，而非重复订单关联、自由 SQL 或新增 Agent。完整选型见 [010](../research/010-refund-change.md)，运行见 [退款说明](../../experiments/refund-change/README.md)。

样例两期 50→10 元，变化 -40 元；退款 3→1 笔、订单 2→1 单；商品归属金额覆盖率 60%→100%。P1 -20、P2 -10、P3 +10 元，另有未归属部分 -20 元。总额、来源与商品分项可核对；这不证明退款原因、统计异常或经营收益。

首次两次失败来自测试辅助函数：成功专用 helper 不适合断言 422，改用 HTTP helper 后又遗漏第三个返回值。服务本来正确拒绝无退款能力，保留 [首次](../probes/refund-change-first-2026-11-06.json) 与 [第二次](../probes/refund-change-second-2026-11-06.json)，不包装成产品缺陷。

补充检查发现两项真实边界问题：[修复前 21 项中 2 项失败](../probes/refund-cross-language-before-2026-11-06.json)。Python Decimal 保留负零而 Java BigDecimal 不保留，1000000→999999 分产生 `-0.00` 与 `0.00` 不一致；现统一为 `0.00`，仍保留精确 -1 分差额。Python 按 Unicode 码点排序，Java 默认按 UTF-16 码元排序，特殊商品编号并列时会误拒绝；Java 现显式按码点比较。最终 21/21。原销售/标量比较使用类似百分比逻辑，其负零边界列入下一稳定性审计，不在此阶段宣称已修复。

浏览器截图保存在忽略目录 `.local/refund-change/browser/`。演示进程已正常停止，历史保留。此次没有新增付费调用；共享账本仍为 65 次历史请求、保守占用 0.314730 元/5 元。

## 基线、局限与后续

开发前 197 个源文件归档 `.local/baselines/before-refund-change-20261106/source.tar.gz`，SHA-256 `b996be29d65fa0657036cd039defb6f138ed74b0fd287638898bedf42613b04e`；开发后归档见 `.local/baselines/after-refund-change-20261106/manifest.json`，归档逐项校验，源码清单不含运行数据和凭据。

Java 负责可信 Worker 的输入绑定与算术校验，不是独立数据库真值验证。评测器通过重建数据库和重建报告检查发布结果；人工期望检查业务答案。真实模型需个人终端的专项/后续合并评测，旧阶段 2h 的真实通过率不自动适用于已修改 Prompt 的当前版本。

面试可讲：运营想知道退款变化集中在哪里；我先复现错误关联会将 50 元放大为 80 元，再根据同类产品确定事件时间和退款粒度；通过命名工具、缺失归属单列、独立总额勾稽和发布校验实现；不仅覆盖部分退款、空期和 Top N，还发现并修复 Java/Python 负零与 Unicode 排序契约问题。验证是合成数据与离线工程测试，不声称真实商家收益。

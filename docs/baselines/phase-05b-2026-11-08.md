# 阶段 5b：停写备份、空目标恢复与数据库权限

日期：2026-11-08。范围：个人项目、合成输入、项目内临时 PostgreSQL 18.6；零真实模型调用。

## 问题、调研与选择

5a 有业务库和迁移，尚无统一备份入口。只复制业务库会漏掉 checkpoint、内部身份与累计模型费用；此为已观察的能力缺口，不是发生过的数据丢失事故。状态接口另有固定显示 H2 的实际问题。

依据与备选见 [部署研究](../research/016-deployment-and-database.md#5b-备份与权限的进一步选择2026-11-08)。采用 PostgreSQL 原生 dump/restore、停写维护窗口、应用状态文件完整性清单；数据库账户是专用 schema owner，不具有集群管理权。没有引入热备、跨存储事务或多副本。

改动前源码：`after-postgres-20261108`，317 文件，SHA-256 `ad65b2b0e49bb3acfa9352d0d55141cf84b6012927aea39126651e68d6f73b20`，归档保存在忽略目录 `.local/baselines/`。

## 实际实现

- `scripts/backup_state.py`：备份原生数据库 dump、owner 哈希/内部 token、Agent runs 和累计预算；校验代码/提示/锁文件/制品版本、文件集合和 SHA，拒绝符号链接、已有恢复目录与非空数据库。
- `scripts/state_guard.py`：启动器、直接 Agent、密码设置共享访问，备份恢复独占访问；额外检查数据库无其他连接。失败恢复留下 `RESTORE_INCOMPLETE`，应用禁止启动。
- `scripts/web_demo.py --postgres`：显式传入三个数据库变量，保持无配置时的 H2 本地入口，退出时回收本次 Java/Worker 子进程。
- PostgreSQL profile 正确显示 `postgres_single_instance`；`deployment/database-privileges.sql` 约束数据库与 schema 权限。Flyway 仍需要 schema DDL 权限，不声称纯 DML 最小权限。

## 限制与面试说明

这是同一版本的单实例停写恢复。源码与 jar 一致性严格校验，不等同于跨版本升级；迁移由 Flyway 另行验收。没有 RPO=0、PITR、热备或多活保证。只接受自己的可信备份；SHA 不是签名。用户必须保存备份之外的数据库连接配置，在最新预算对账前不能用旧备份恢复付费执行，更不能同时运行两个实例消费同一预算。

可复述：业务库恢复不等于 Agent 系统恢复。我把业务任务、模型检查点、登录身份和费用账本作为一次停写维护的恢复单元，借助成熟 PostgreSQL 工具而非自写数据库导出。验证重点是能否继续原任务、是否重复发布/调用以及预算是否连续，而不只是“备份文件生成成功”。

# 阶段 3a · 稳定性与资源边界

状态：资源控制专项验收完成；登录保护与部署仍在后续阶段。只使用个人项目、隔离临时库、回环服务与合成数据，没有真实模型请求。

## 前后变化与取舍

已有任务系统能处理幂等、租约 fencing、取消、重试和重启，但没有任务总量/活跃量/有效租约上限，也没有跨心跳的绝对截止时间。Worker 仅在退出后检查结果大小。销售工具与标量比较还存在 Python `-0.00` 被 Java 拒绝的边界问题。

调研 Celery、LangGraph、Spring Boot/Micrometer 与 Metabase 后，选择补齐现有数据库事务边界，不为单实例有限任务引入 broker 或监控集群。理由、官方链接与预先验收约定见 [012](../research/012-reliability-controls.md)。

现在同一工作空间的创建和领取共享数据库锁：配额检查与入队处于事务内，幂等重放不消耗额度；导入超限时上传事务也回滚。任务固定截止时间并独立扫描，持续心跳和重启都不能延长；旧 Worker 仍不能发布。增加受保护的业务状态汇总、Worker 输出增长检测及中文错误说明。百分比零表示统一，真实 Java 发布通过。

默认保留 2000 个任务、活跃 32、有效租约 4、最长 15 分钟。这些是容量政策，不是测出的吞吐量。历史不自动删除、归档不等于删除；输出检查不是 OS 级磁盘沙箱。仍是单空间、单 JVM、H2 文件数据库，不能宣称多租户或生产高可用。

面试可讲：可靠性不止是“加了重试”。先列出任务生命周期和资源上限，再用并发创建、过期租约、持续心跳、Worker 卡死等反例验证；区分请求幂等、有效执行权和结果发布，不承诺模型调用 exactly-once。预算先预留、未知费用不释放，业务报告则只能由当前有效租约发布。

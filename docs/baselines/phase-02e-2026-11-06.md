# 阶段 2e：销售变化来自哪些商品

日期：2026-11-06。状态：支付口径的商品贡献工具、Java 任务、离线 LangGraph 接入、网页已完成本机工程验收；新能力的真实模型自然语言评测与商家价值尚未验证。

## 问题与取舍

阶段 2d 能接入外部账本、比较总额，但不能分解到商品。基线实际查询：第一期总支付 280 元，第二期 150 元；现有“含商品订单总额”分别查询 P1/P2/P3 得到 180/100/100 元，相加 380，不能当商品明细分摊。原指标按其定义正确，本次是补分析能力。见 [改造前实测](../probes/sales-change-before-2026-11-06.json)。

调研 Shopify 的商品销售口径、Power BI 的正负贡献和 Other、Tableau 的关联/因果边界；比较逐商品问答、自由 SQL/多 Agent、完整 BI 引擎和专用工具，选择**固定参数的确定性商品分解工具＋既有单 Agent**。只有一个可加金额指标与商品维度，现阶段不需要额外 Agent，避免把数值正确性交给模型协调。完整来源、日期、公式、替代方案与预设验收见 [007 研究记录](../research/007-sales-change.md)。

- 原 Agent/任务 **42/42**（29.190 秒）、导入 **25/25**（10.703 秒）、网页 **11/11**（13.133 秒）、全数据 **70/70**（6.716 秒）回归通过：[Agent](../probes/sales-change-agent-regression-2026-11-06.json)、[导入](../probes/sales-change-import-regression-2026-11-06.json)、[网页](../probes/sales-change-web-regression-2026-11-06.json)、[数据](../probes/sales-change-data-regression-2026-11-06.json)。不同套件包含重复的计算用例，不求和宣称独立用例总数。
- 固定样例：280 → 150 CNY，变化 **-130 / -46.43%**。P3 -100、P2 -40，P1 +10；全部下降 -140，被增长 +10 部分抵消，P3 占下降金额 **71.43%**。商品两期金额及 delta 分别与订单总额完全相符。
- top_n=1 时仍保留其他下降 -40；同一订单多个相同商品明细不会重复计整单金额，多笔退款不会扩行或冲减该支付口径。15 套固定随机种子数据与独立 Python 遍历汇总一致。
- 零基数、双方无额、正负抵消净零、取消单、时区偏移与半开边界、同幅度排序、大金额差 1 分、包含 SQL 字符的商品 ID 均有覆盖；不可比期间、越权、未确认数据、旧模型许可、伪造证据、错误来源/期间/百分比/守恒会被拒绝。
- 两套字段/单位/时区不同的已确认导入都得到相同业务分解，其中一套没有退款表仍可分析。新增分析前后数据版本元数据不变。
- 真实 LangGraph＋脚本模型＋Java 完成导入版本分析，**1 次业务工具、2 次脚本模型调用、0 次真实调用**；内部 SQL 为三条，不能把一次工具调用说成只执行一次 SQL。错误参数后修正可成功，模型夹带的“999999 元/涨价导致”文本不进入发布报告。
- 浏览器真实任务 `03b84370-07cc-4510-b404-d337ef841f7f` 使用阶段 2d 已确认中文导入修订 2，显示上述商品贡献；下载报告与来源 SHA、数值核对一致。空区间任务 `72f4072f-b4b3-4497-bdc2-65e40a3faa16` 显示 0 个期间有额商品，变化率不计算。刷新、重启、任务跳转及浏览器返回已检查，修复后控制台错误/警告查询为空。见 [浏览器记录](../probes/sales-change-browser-2026-11-06.json)。

## 观察到的问题与修复

浏览器仅修改同页 `#task=...` 时，地址中的任务已变化，但页面仍显示前一个任务。原因是原页面只在初始化读取 hash，缺少后续路由监听。增加 hashchange 处理，复用现有任务轮询与 generation 过期响应保护；观察到两任务切换及浏览器返回均显示正确结果。该问题与计算无关，保留在本阶段验收记录，不把它冒充模型质量提升。

## 边界与下一步

这是商品层面的**描述性金额贡献**。只能分析已确认分摊的支付金额，不扣退款；没有数量、原价/折扣、流量、库存等数据，不能继续拆价格/销量因素或宣称缺货/广告原因。当前只有 product_id，没有商品名称补全或任意维度钻取。限制来自现有数据，不能用 Prompt 补造事实。

有差值不等于异常，也不等于已找到经营原因。固定快照的缺记录与真实零交易仍依赖导入者的完整性声明。Top N 之外保留汇总贡献，当前不提供全部商品明细分页导出。网页只支持整日 UTC，API/工具支持明确带偏移的时间；不做任意时区日历或季节性调整。

本阶段 **0 次新增真实模型调用**；既有个人账本仍为 35 次、0.137988 元保守上界。合成数据、脚本模型测试只证明工程行为，新工具自然语言选择和澄清质量未验收，不能套用阶段 2b 的 85.7%。下一步应对新经营问题建立独立真实模型评测，再按相同流程推进退款变化定位或更深分析；多 Agent 需要对照证据。功能完成后再整体美化前端。

## 面试复述

“我先发现总额比较无法解释商品贡献，而原来‘包含商品的订单总额’在跨商品相加时会重复计入。参考 Shopify 的粒度口径、Power BI 的正负贡献和 Other，选用确定性商品分解工具。按已确认的明细金额聚合，用独立订单总额做勾稽，分别展示下降和增长，保留其他贡献，处理零基数。Java 管任务和结果绑定，LangGraph 只选择工具和引用证据。样例 280 降到 150，能核对到 P3 -100、P2 -40、P1 +10；21 项新工程检查与旧功能回归通过。当前只定位金额变化集中在哪里，尚未证明经营原因或真实模型泛化效果。”

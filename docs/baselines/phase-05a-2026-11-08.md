# 阶段 5a：真实 PostgreSQL 与版本迁移

日期：2026-11-08。状态：业务 PostgreSQL 路径、版本迁移与相关行为已验证；完整部署交付继续推进。

## 为什么做、改了什么

原业务层仅支持 H2 文件，启动反复执行 schema，尚不能在独立数据库中验证事务及迁移。[研究 016](../research/016-deployment-and-database.md) 对比最少挂盘、全面迁移所有状态、业务库先迁三种方案；选择业务 PostgreSQL＋应用持久卷。H2 保留本地演示，避免拿兼容模式冒充真实跨库支持。DuckDB 仍做分析，Java 业务库负责任务和数据版本，两者职责不同。

增加 Spring Boot 4.1.2 管理的 PostgreSQL JDBC 42.7.14、Flyway 12.4.0；`postgres` profile 要求显式连接配置，使用 V1 迁移，校验 checksum，关闭自动 clean 和未知库 baseline。默认 H2 不启用 Flyway。PostgreSQL V1 把 H2 的 CLOB/特殊 MERGE 改成 TEXT/一次性初始化；没有重写业务任务与导入代码。

项目内从官方 SHA 固定源码编译 PostgreSQL 18.6，运行临时集群与原真实 Java/Worker/DuckDB 契约。工具链与数据全在 `.local`，没有安装系统服务、访问既有库或公司 Docker daemon。源码下载原时限短于实际传输预估，已明确停止自己的旧会话、保留约 10.5 MB 并续传，最终 SHA 一致后才编译。

Java 启动器增加项目内 Linux 普通 JDK 目录识别，仍不查找机器 PATH 上的 Java，不读取公司配置；本机原 JDK 21.0.13 识别通过。此改动不等于 Linux/容器已验收。

| 检查 | 实际结果 | 原始记录（`docs/probes/`） |
| --- | --- | --- |
| 新依赖/生产 profile 构建 | Maven 构建通过 | 本机 `.local/postgres-api-build.log` |

| 真实 PG 首轮 | 44 项中 43 通过、1 测试断言失败；总流程 60.143 秒 | `postgres-first-2026-11-08.json` |
| 修正反例并新增迁移失败检查 | 3/3；总流程 10.180 秒 | `postgres-migrations-2026-11-08.json` |

首轮失败不在业务实现：将整份旧 H2 schema 发给 PostgreSQL 时，解析器先拒绝 `MERGE ... KEY`；测试误以为先报告 CLOB 类型。修正后分别验证完整脚本的语法拒绝和首条建表的 CLOB 拒绝，两个不兼容点均有实际证据。没有隐藏首轮失败，也没有声称做过一次“46/46”全量运行。

新迁移检查验证：改动已执行迁移 checksum 后应用拒绝启动；新增 V2 中先建表再故意失败，PostgreSQL 回滚新表且已成功的 V1 保留，恢复正常配置后可启动。任务回归覆盖并发幂等、租约 fencing、重复回执、取消、进程终止/重启；导入路径覆盖映射确认、版本、归档及网页行为。测试集重用证明既有契约跨库保持，不是新增商家效果或高负载基准。

旧 H2 回归器仍有固定 2026-11-06 日期字段，本次实际执行为 2026-11-08；见文件名与本记录。所有上述检查没有真实模型调用。模型账本未知占用情况仍以阶段 4b 为准。

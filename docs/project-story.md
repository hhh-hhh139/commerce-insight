# 项目讲解、前后对比与演示

更新：2026-11-08。这是当前已实现版本的讲解稿，发布/Linux/真实模型待验收项会随证据更新。不是提前填写的上线成果。

## 一句话

基于 Java 业务后端与 Python LangGraph 构建电商经营分析助手，支持外部账本映射确认、销售/退款变化分析和报表差异核对，以确定性工具生成金额与证据，并用持久任务、检查点、独立预算和故障评测保障可追溯执行。

## 简历四点（当前可以使用的版本）

1. 设计 Java/Spring Boot 与 Python LangGraph 的职责边界，实现 HTTP 持久任务队列、幂等键、租约 fencing、心跳、取消与截止；通过真实 JVM/HTTP/DuckDB/图状态的 42 项任务及 Agent 工程回归。
2. 构建外部电商账本适配与证据查询层，支持字段/状态/金额单位/时区映射、质量检查及不可变版本；基于 DuckDB 和整数金额实现商品销售贡献、退款归属与报表差异重算，避免多表关联重复计金额。
3. 接入 LangGraph 单 Agent、受控工具和结构化结果校验，建立开发/保留题及独立数值审计；历史商品贡献专项 9 题、15 次真实模型任务，保留集两轮各 6/6，通过全部报告数字和引用重算，同时保留失败与适用边界。
4. 实现单店主 Spring Security/CSRF、累计费用预占、模型错误诊断、PostgreSQL/Flyway 与停写备份恢复；完成跨业务库/Agent 状态恢复和实际 Caddy HTTPS 链路验证，并准备可复现容器与 Linux CI。

第四点在 CI 实际通过前只能写“准备”，不能写“已容器化上线”。第三点必须保留“小样本/历史版本/合成题”语境，不把 12/12 写成通用准确率 100%。代码由 AI 协助开发，应说明自己的需求、方案判断、核验和失败分析贡献，能现场解释关键路径后再声称熟练掌握。

## 先讲问题，再讲组件

目标用户是假设中的能导出订单/售后账本的中小商家或运营。一次“这周销售下降了多少”至少有三个问题：销售定义是什么、哪个时间范围、是不是把订单与多条明细/退款 JOIN 后重复求和。模型即使生成流畅 SQL，也可能在这些地方算错。

因此先做显式数据契约与命名工具，再让模型选择工具和判断信息是否充分。最小基线是固定指标查询，而不是直接引入专家团队。Java 管授权、数据版本和谁能发布结果；LangGraph 管一次推理中的工具调用与恢复。两种状态不是一回事，检查点不能替代幂等、租约和业务事务。

每个改动按用户要求留存：可复现问题 → 官方同类资料 → 最小备选 → 选择理由 → 源码快照 → 实验及原始失败。具体引用以各模块研究为准；[JD 映射](job-alignment-2026-11-05.md)只支持能力准备方向，不证明用户需求。

## 五分钟演示（默认不花模型费）

1. 打开工作台，说明合成数据和指标定义，查询两期销售 280→150 元；指出 P3 −100、P2 −40、P1 +10 与总变化 −130 的勾稽。
2. 展开证据，指出查询时间、数据 SHA、SQL 与参数；解释模型并不生成金额。
3. 在数据管理上传 `examples/imports/renamed-major/` 的三份 CSV，确认列名/状态/金额单位及时间映射，通过质量检查后确认版本；说明未经确认的数据不能分析、默认不能发给模型。
4. 展示退款变化，区分退款发生期与订单支付期，指出未知商品归属不能悄悄分配；再展示报表口径差异与剩余偏差。
5. 展示任务历史/取消/导出，退出后确认旧页面不能继续取数据；展示一份标注日期的历史模型报告与对应评测，不冒充正在调用模型。

需要现场自然语言演示时，应预先完成当前版本真实模型验收、价格和预算核对，使用自己的终端隐藏输入 Key；不要在面试现场临时删除账本或绕过限制。

## 必须能回答的追问

- **为什么 Java + Python？** Java承接用户、事务、任务状态和授权，Python 使用成熟 Agent/数据生态；跨进程协议成本通过明确请求/结果契约承担。
- **为什么不用 Celery/Kafka？** 当前单实例、有限并发，业务表可承担持久准入与租约；并不是说队列无用，扩容与更复杂投递是重新选型条件。
- **为什么 LangGraph？** 用现成框架的工具循环、结构化决策和 checkpoint，避免自行维护完整图执行器；但业务任务协议、金额语义和发布校验仍需应用实现。
- **为什么没有默认多 Agent？** 已有强单 Agent和同工具候选对照，额外专家必须有质量/成本证据。当前真实对照缺失，因此保持单 Agent 是有依据的决定。
- **能保证 exactly once 吗？** 不能对外部模型调用承诺。业务结果靠幂等与租约校验避免重复发布；模型在请求已发出、checkpoint 尚未提交时可能状态未知，独立预占账本保留风险并阻止盲目重试。
- **备份数据库为什么不够？** Agent checkpoint 与费用账本在应用卷；一次停写维护需备份两者，并实际验证续跑/预算连续性。
- **这个项目价值验证了吗？** 工程任务和合成业务口径有证据；没有商家试用，不能说节省了多少运营工时。下一步按[试用协议](trial-protocol.md)记录任务完成率、困难和反馈，区分同学易用性测试与真实商家需求。

## 用户与价值假设

首要用户是假设中的中小电商团队运营人员或商家：能导出订单、商品明细和部分售后数据，需要反复核对指标、定位变化，但缺少专职分析支持。

希望改善的任务是从提问到核查数字、定位变化集中区域、形成有证据的结论。实际需求频率、使用门槛和节省时间尚未经过访谈验证。

用户目前没有可联系的试用者或私有数据，已选择先使用可公开的数据与样例。公开演示提供样例任务；后续自部署允许接入授权数据。产品价值需通过实际试用补充验证，不能用演示访问量或合成题成功率替代。

## 首版业务边界

| 任务 | 所需数据 | 输出及边界 |
| --- | --- | --- |
| 销售变化分析 | 订单、商品明细、金额、状态和时间字段 | 指标及分组贡献；标明金额定义、时间范围与对比基准 |
| 退款变化定位 | 订单、退款记录、退款状态与时间；可选商品归属 | 退款变化集中区域；已关联商品和未归属金额分别披露，缺失时不声称完整商品结论或统计异常 |
| 报表差异核对 | 两份报表及其原始数据、口径或映射 | 解释时间、状态、关联粒度等可验证差异；证据不足则列待核对项 |

支付、结算与到账分析是后续可选扩展，只有数据足够时开放。首版不覆盖广告投放优化、库存预测、自动经营操作和任意行业分析。

首个纵向闭环：导入订单与明细 → 查看质量检查 → 确认口径 → 提问销售变化 → 执行查询 → 展示数字与证据 → 查看任务记录。退款和报表核对随后加入，避免首批实现同时覆盖所有输入类型。

数据适配目标是同类电商数据换列名、状态编码或表关系后，通过明确映射接入；跨行业或没有业务含义的数据不保证自动理解。映射与指标版本必须进入分析记录。

Java 的业务任务状态与 Python 的图执行状态要有清晰对应；重试、重复投递、取消、恢复时只能有一个有效结果被发布。该契约需单独研究和实验，不能把 LangGraph checkpoint 当成完整调度系统。

当前采用 HTTP JSON＋Java 持久化任务表＋Python 拉取，任务展示先轮询；事件流、生产数据库及复杂调度另行比较验收，依据见 ADR 002。暂不预设需要微服务集群、Kafka 或 Kubernetes。

单 Agent 是初始质量基线。复杂任务中的销售分析、售后分析可作为专家分工候选；仅在上下文隔离、独立调查和实测效果支持时启用。数值校验与权限控制由代码承担。

## 评测维度

- 正确性：数值、分组、筛选、口径、时间范围与引用是否一致。
- 可信度：证据是否支持结论；信息不足是否澄清；是否把相关性写成因果。
- 可靠性：超时、模型错误、工具错误、重启、重复请求、取消及权限失败的行为。
- 效率：端到端耗时分布、模型与工具调用数、实际 usage、费用及预算触发。
- 可移植性：更换同类数据映射，核心 Agent 流程是否无需修改。
- 可使用性：导入与确认是否清楚，结论是否能帮助完成具体任务；真实用户项单独记录。

基准题按问题族拆分开发与保留集，避免相同模板改写同时进入两侧。真实模型多次运行报告分布与失败样本；离线回放与实时外部服务结果分别记录。
